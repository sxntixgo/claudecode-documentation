\chapter{The Plugin Ecosystem}
\label{ch:plugin-ecosystem}

Claude Code ships with a powerful built-in skill set: it reads files, writes
code, executes shell commands, and understands entire codebases. Yet many of
the most valuable development tasks require reaching \emph{outside} that
baseline — querying a live database, fetching current documentation, automating
a post-commit hook, or packaging a multi-step review process so the whole team
runs it consistently. The plugin ecosystem is how you add those capabilities.

\index{plugin ecosystem}
\index{extension types}

\section{Extensions vs.\ Plugins}
\label{sec:extensions-vs-plugins}

Two words appear repeatedly in Claude Code's documentation and they mean
different things:

\begin{itemize}
  \item \textbf{Extension types} are the four primitives that change what
        Claude can do: \emph{MCP servers}, \emph{skills}, \emph{hooks}, and
        \emph{slash commands}. Each lives in \texttt{.claude/} in your
        project. This chapter — and most of the book — is about these.
  \item \textbf{Plugins} are \emph{installable bundles} that package one or
        more of those extensions (plus optional LSP servers, background
        monitors, and bin executables) behind a single
        \texttt{plugin.json} manifest. You install a plugin in one
        command and uninstall it the same way.
\end{itemize}

You can build everything described in this book without ever creating a
plugin; the standalone \texttt{.claude/} directory is sufficient. Plugins
matter when you want to \emph{share} a configuration with your team or the
community.

\section{The Four Extension Types}
\label{sec:four-types}

Think of Claude Code as a smartphone: capable out of the box, but transformative
once you install the right apps. The four extension types are the apps.

\begin{itemize}
  \item \textbf{Connect to external tools} — GitHub, databases, APIs —
        via \emph{MCP Servers};
  \item \textbf{Define reusable workflows} — code review checklists, deployment
        pipelines — via \emph{Skills};
  \item \textbf{Automate repetitive actions} — format on save, test on commit —
        via \emph{Hooks};
  \item \textbf{Create keyboard-friendly shortcuts} for any workflow via
        \emph{Slash Commands}.
\end{itemize}

Each type solves a distinct class of problem.

\subsection{MCP Servers}
\index{MCP Server}

\textbf{Model Context Protocol (MCP) servers} are programs that implement the
open MCP standard to expose tools and data sources to Claude Code. An MCP
server can wrap a REST API, a database driver, a search engine, or any
executable — giving Claude structured, authenticated access to it.

Without the GitHub MCP server, asking Claude to ``create a pull request'' yields
a manual instruction to visit a browser. With it, Claude issues the API call
directly and returns the PR URL. The protocol is described in full in
\cref{ch:mcp-servers}.

\subsection{Skills}
\index{Skills}

\textbf{Skills} are Markdown files (\texttt{SKILL.md}) that define how Claude
should execute a repeatable workflow. A code-review skill might specify which
security checks to run, which formatting rules to enforce, and which model to
use — once. Everyone on the team who invokes \texttt{/code-review} gets the
same systematic process. Skills are covered in \cref{ch:skills}.

\subsection{Hooks}
\index{Hooks}

\textbf{Hooks} execute shell commands automatically in response to Claude Code
events: before a tool runs (\texttt{PreToolUse}), after it completes
(\texttt{PostToolUse}), when a notification fires, or when Claude stops
responding. They are configured in \texttt{.claude/settings.json} and require
no code — just the commands you want to run. See \cref{ch:hooks}.

\subsection{Slash Commands}
\index{Slash Commands}

\textbf{Slash commands} (\texttt{/command-name}) are Markdown files stored in
\texttt{.claude/commands/} that Claude interprets as a prompt template when
invoked. They accept arguments via the \texttt{\$ARGUMENTS} variable and are
the lightest-weight way to package a workflow. They are detailed in
\cref{ch:commands}.

\section{How the Four Types Work Together}
\label{sec:plugin-synergy}

The real power emerges when types are combined. Consider an automated code
review pipeline:

\begin{enumerate}
  \item A \textbf{Hook} (\texttt{PreToolUse} on \texttt{Bash}) triggers the
        review before every commit.
  \item A \textbf{Skill} (\texttt{code-review}) guides Claude through security
        checks, style enforcement, and test coverage analysis.
  \item An \textbf{MCP Server} (GitHub) lets Claude post inline comments
        directly on the pull request.
  \item A \textbf{Slash Command} (\texttt{/review-pr}) gives the team a manual
        trigger for the same workflow on demand.
\end{enumerate}

Each piece is reusable independently, but together they form a consistent,
automatable process.

\section{Configuration Layout}
\label{sec:config-layout}

All plugin configuration lives under \texttt{.claude/} in your project root
(or in user-level config at \texttt{\textasciitilde/.claude/}):

\begin{lstlisting}[language=bash,caption={The \texttt{.claude/} directory structure}]
your-project/
  .claude/
    settings.json      # global settings, hooks, MCP servers, default model
    commands/          # slash command definitions
      review.md
      deploy.md
    skills/            # skill definitions
      code-review/
        SKILL.md
\end{lstlisting}

MCP servers are configured inside \texttt{settings.json} under the
\texttt{mcpServers} key, or added interactively with \texttt{claude mcp add}.

\begin{lstlisting}[language=json,caption={Minimal \texttt{.claude/settings.json} with one MCP server and one hook}]
{
  "defaultModel": "claude-sonnet-4-6",
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_TOKEN": "${GITHUB_TOKEN}"
      }
    }
  },
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write",
        "hooks": [{"command": "npm run format -- --write $FILE"}]
      }
    ]
  }
}
\end{lstlisting}

\begin{notebox}[Security note]
Never hardcode secrets in \texttt{settings.json}. Always use environment
variable references such as \texttt{\$\{GITHUB\_TOKEN\}} so that sensitive
values are read at runtime and never committed to version control.
\end{notebox}

\section{Plugins: Installable Bundles}
\label{sec:plugin-bundles}

\index{plugins!bundles}\index{plugin marketplaces}

A plugin is a directory containing a \texttt{.claude-plugin/plugin.json}
manifest plus any combination of:

\begin{itemize}
  \item \texttt{skills/}, \texttt{commands/}, \texttt{agents/},
        \texttt{hooks/} — same files you would put in
        \texttt{.claude/}, but bundled;
  \item \texttt{.mcp.json}, \texttt{.lsp.json} — MCP and LSP server
        configurations;
  \item \texttt{monitors/}, \texttt{bin/}, \texttt{settings.json} —
        background monitors, executables, and default settings.
\end{itemize}

When you install a plugin, all of its skills become available as
namespaced commands (\texttt{/plugin-name:skill-name}), agents appear in
\texttt{/agents}, hooks register, and any bundled MCP servers start.

\subsection{Marketplaces}

Anthropic maintains two public marketplaces:

\begin{itemize}
  \item \texttt{claude-plugins-official} — curated by Anthropic, always
        available in every Claude Code installation.
  \item \texttt{claude-community} — community submissions reviewed before
        listing. Add it with
        \texttt{/plugin marketplace add anthropics/claude-plugins-community}.
\end{itemize}

\begin{lstlisting}[language=bash,caption={Installing a plugin from the official marketplace}]
# Browse and install interactively
/plugin

# Install a specific plugin
/plugin install superpowers@claude-plugins-official
/reload-plugins
\end{lstlisting}

For local development you can load a plugin directly without installing:
\texttt{claude --plugin-dir ./my-plugin} or
\texttt{claude --plugin-url https://example.com/my-plugin.zip}.

\section{Plugin Discovery}
\label{sec:plugin-discovery}

\textbf{Official sources}

\begin{itemize}
  \item \textbf{Plugins}: browse \texttt{claude-plugins-official} from
        inside Claude Code with \texttt{/plugin}.
  \item \textbf{MCP servers}: the Anthropic Directory at
        \url{https://claude.ai/directory} catalogs reviewed connectors,
        each installable with \texttt{claude mcp add}.
  \item \textbf{Skills}: the community superpowers collection at
        \url{https://github.com/obra/superpowers} provides production-ready
        skills for common workflows. Install with
        \texttt{/plugin install superpowers@claude-plugins-official}.
\end{itemize}

\textbf{Community sources}

Search GitHub for the topic \texttt{mcp-server} or \texttt{claude-skill}, or
browse the \texttt{awesome-claude-code} curated list
(\url{https://github.com/hesreallyhim/awesome-claude-code}).

\section{Choosing the Right Plugin Type}
\label{sec:choosing}

Use this decision guide when you encounter a new automation need:

\begin{itemize}
  \item \textbf{Need real-time external data or API actions?} $\Rightarrow$
        MCP Server (\cref{ch:mcp-servers})
  \item \textbf{Need to document and share a multi-step workflow?} $\Rightarrow$
        Skill (\cref{ch:skills})
  \item \textbf{Need to run a command automatically on every tool use?}
        $\Rightarrow$ Hook (\cref{ch:hooks})
  \item \textbf{Need a quick one-liner shortcut for a canned prompt?}
        $\Rightarrow$ Slash Command (\cref{ch:commands})
\end{itemize}

\section{Best Practices}

\begin{itemize}
  \item \textbf{Version-control \texttt{.claude/}.} Committing skills, hooks,
        and commands ensures the whole team uses the same configuration.
  \item \textbf{Keep plugins focused.} A skill that does one thing well is
        easier to maintain than one that handles every case.
  \item \textbf{Use descriptive names.} \texttt{code-review-security} is
        discoverable; \texttt{cr} is not.
  \item \textbf{Never hardcode credentials.} Use environment variable
        references in all configuration files.
\end{itemize}

\section{Exercises}
\label{sec:plugin-exercises}

\begin{exercisebox}[Exercises — set up your project's \texttt{.claude/} directory]
Throughout the next several chapters you will build up a working
configuration for a small project (any Node.js, Python, or Go service of
yours will do). These first exercises lay the foundation; later chapters
extend it.

\begin{enumerate}
  \item In your project root, create the directory tree:
\begin{verbatim}
.claude/
  settings.json
  commands/
  skills/
  agents/
\end{verbatim}
  \item Write a minimal \texttt{.claude/settings.json}:
\begin{verbatim}
{
  "defaultModel": "claude-sonnet-4-6"
}
\end{verbatim}
        Start a Claude Code session in the project and run \texttt{/help}.
        Confirm Claude picks up the directory (the prompt header should
        show the project root).
  \item Add \texttt{.claude/} to version control with
        \texttt{git add .claude/}. Commit it. Confirm
        \texttt{settings.json} is committed but \texttt{settings.local.json}
        (which you will create later) will be ignored.
  \item Identify which of the four extension types you would use for each
        of these needs. Write your answer in one line each:
        \emph{(a)} run \texttt{npm run lint} after every file write;
        \emph{(b)} package a standard PR-review workflow for your team;
        \emph{(c)} let Claude query your staging Postgres database;
        \emph{(d)} let a teammate type \texttt{/deploy staging} to run a
        deploy script.
\end{enumerate}
\end{exercisebox}
